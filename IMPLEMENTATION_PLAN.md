# MVP tracer-bullet implementation plan

## Objective

Deliver the complete iPhone MVP defined by [MVP_DESIGN.md](MVP_DESIGN.md) as a sequence of small vertical slices. Every product commit must connect visible UI to production implementation and persistence, include programmatic verification of nonvisual behavior, and add or extend an exact-pixel E2E journey.

The sequence deliberately avoids horizontal “build all models, then all screens” phases. A tracer is only complete when a listener can perform its narrow journey through the real app.

## Delivery model

### Stacked commits and pull requests

Each tracer is one commit and one stacked draft PR unless a mechanical follow-up is required to repair that tracer’s CI. Branches use `agent/tracer-XX-description` and are based on the preceding tracer commit.

```text
main / T00 foundation
└── T01 single-book import + playback
    └── T02 position restoration
        └── T03 format and chapter parity
            └── …
```

Only two or three dependent PRs stay open at once. This preserves overlap without making rebases and screenshot-baseline changes unmanageable.

### Overlap loop

For every tracer `Tn`:

1. Finish its production path, tests, generated walkthrough, and reviewed screenshots.
2. Commit and push `Tn`; open or update its draft PR.
3. Record its exact head SHA and let CI run for that SHA.
4. Immediately branch `Tn+1` from that commit and begin its independent work.
5. In parallel, inspect `Tn` checks and review feedback.
6. If `Tn` needs a fix, pause dependent file edits at a safe boundary, apply the focused fix to `Tn`, verify, then rebase `Tn+1`.
7. Merge strictly in order. Retarget/rebase the next PR, regenerate the Xcode project, and rerun every affected prior journey.

Do not push `Tn+1` onto the `Tn` branch merely to replace an in-progress CI run. Each SHA remains independently auditable.

### Definition of done for every tracer

- The commit builds from a clean checkout with the pinned toolchain.
- The new journey uses production services behind injected boundaries; views do not branch on fixture names.
- Unit/integration tests cover parsers, transactions, clocks, filesystem changes, or playback events that screenshots cannot prove.
- The E2E step helper programmatically verifies the intended state before every capture.
- All prior E2E stories still pass semantic and exact-pixel comparison.
- The new story’s README and reviewed PNG baselines are committed.
- IDs, dates, playback positions, progress, locale, appearance, and system chrome are deterministic.
- Schema changes include a forward migration and a fixture for the previous schema.
- Source media remains unchanged; checksums prove this where import/edit behavior is involved.
- CI is green for the exact commit SHA before its PR is merged.

## Test-media policy

### Committed fixtures

CI uses tiny synthetic audio generated by repository-owned tooling. Fixtures must be legally redistributable, deterministic, and just long enough to validate seek, transition, chapter, tag, and interruption behavior. Synthetic fixtures may include:

- short M4A, M4B, and MP3 files;
- two- and three-part books with controlled disc/track tags;
- embedded artwork created for tests;
- chapter metadata with known boundaries;
- corrupt, truncated, Unicode, duplicate, and unsupported cases;
- safe and hostile ZIP archives.

### Local full-book fixture

`books/` remains ignored and is never copied into Git history, CI artifacts, screenshots, logs, or support bundles. The current local sample contains 30 ordered MP3 parts, approximately 891 MiB and 16 hours of audio. It is useful for realistic grouping, progress, cancellation, relaunch, storage, cross-track seek, and long-playback smoke tests.

An opt-in runner accepts `LOCAL_AUDIOBOOK_FIXTURE` and stages that path into a disposable simulator. Assertions use neutral facts such as file count, readable duration, ordering, and source checksums; they never snapshot or print the title, cover, synopsis, or contributor metadata. The runner deletes its own simulator afterward.

## Foundational test-harness work

The current runner is intentionally one-story-specific. T01 must generalize it before product work expands:

- accept a story identifier and test selector;
- isolate `.xcresult`, attachments, actual walkthrough, and baseline paths per story;
- export screenshot filenames from the generated step manifest rather than a hard-coded list;
- make `TestStepHelper` receive story metadata, fixture facts, and preconditions;
- support multi-step and multi-test stories without attachment collisions;
- run one story locally or the full ordered suite;
- record only when an explicit flag names the story being updated;
- never record in pull-request CI;
- upload actual walkthrough and `.xcresult` on failure;
- assert Xcode build, runtime identifier, simulator type, and architecture before comparison.

## CI and baseline policy

- GitHub Actions pins Xcode 26.6, iOS 26.5, iPhone 17, arm64, light appearance, standard Dynamic Type, locale, time zone, and status bar.
- Preflight fails with a precise environment mismatch before building.
- Build, test, attachment export, materialization, and comparison are separate steps so failure artifacts survive.
- Pull requests can compare but cannot record baselines.
- A baseline changes only when the PR explains the visual decision and includes the generated walkthrough diff.
- Exact-pixel mismatch is never fixed by tolerance, masking, retry, or an unpinned environment.
- CI status is checked by run ID and commit SHA, not only by branch name.

## Dependency and sequencing risks

- T01 stabilizes shared visual components and the generalized runner; late design-token changes otherwise fan out across all baselines.
- Schema and migration fixtures begin in T01, not when backup work starts.
- Moving playback positions require injected engine events; screenshots only capture frozen acknowledged state.
- Share Extension/App Group work waits for a durable import queue in T07.
- ZIP support waits for the grouping model and ships with hostile-input defenses.
- AirDrop is represented by document-open handling because peer transfer is not deterministic in CI.
- No real audiobook content, title, cover, synopsis, or contributor data enters committed fixtures or artifacts.

## MVP completion gate

The MVP is complete only when T00–T19 are merged in order, Stories 001–011 and all nonvisual suites are green on the pinned environment, the opt-in local sample run passes, the accessibility and offline audits are recorded, and every acceptance item in `MVP_DESIGN.md` has evidence or an explicitly documented product decision.
